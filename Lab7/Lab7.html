Horizontal vs Vertical Tiering

Architecting Multi-Model Pipelines: Intra-Vendor Scaling vs Cross-Vendor Equivalence

Which Direction Should We Move?

When an engineering workload requires architectural adjustment, system designers must decide between Vertical Tiering (scaling capability within a vendor family) and Horizontal Tiering (switching providers at a comparable capability level).

Horizontal vs Vertical Decision Framework
VERTICAL TIERING
Same Vendor — Different Capability Tier

Question: "Need more capability or reasoning?"

Move within a single vendor family from FAST → MID → HIGH.

Luna → Terra → Sol
Haiku → Sonnet → Opus
Use when: The task complexity requires deeper reasoning or higher problem-solving capacity.
HORIZONTAL TIERING
Different Vendor — Comparable Capability Tier

Question: "Need another provider option at the same tier?"

Move across vendors at equivalent capability levels (Vendor A ↔ Vendor B).

Sol ↔ Opus / Sonnet
Terra ↔ Haiku 4.5
Use when: Cost, latency, regional availability, governance, or provider resilience favors another model.

# Engineering Task — Debugging Incident INC-8821

## Symptom Report
Production incident INC-8821:
When payment processing fails or payment webhook receives status "FAILED", customer inventory stock remains reserved in `InventoryRecord` instead of being restored.
Additionally, if multi-item stock reservation fails halfway through in `create_order`, previously reserved items in the same request are not restored.

## Requirements
1. Investigate `src/services/order_service.py` (and `handle_payment_webhook`).
2. Identify the root cause of the stock leakage when payment fails or when partial order reservation fails.
3. Fix the defect so that inventory stock is properly released back when payment status is FAILED or when order reservation fails.
4. Preserve existing interfaces and avoid breaking unrelated functionality.

Key Takeaways & Architectural Guidance

  • Vertical Tiering: Move up or down within a single model family (`Luna` → `Terra` → `Sol` or `Haiku` → `Sonnet` → `Opus`) when the task requires more reasoning power or when cost reduction is needed for simpler tasks.
  • Horizontal Tiering: Switch across vendor families at comparable capability levels (`Sol` ↔ `Opus` or `Terra` ↔ `Haiku`) to maintain vendor neutrality, bypass rate limits, or leverage specific provider strengths.
  • Evidence-Driven Decision Making: Always benchmark both vertical scaling and horizontal substitution using empirical metrics (latency, cost, test pass rate) rather than provider marketing claims.
